FLAGSHIP CASE STUDY

Production-Like Splunk Enterprise Security Detection Lab

A lab architecture for demonstrating the complete security analytics lifecycle: telemetry generation and collection, Splunk ingestion, CIM normalization, Enterprise Security detections, Risk-Based Alerting, investigation, and response.

THE PROBLEM

Detection engineering needs a system, not just SPL.

A search can return events and still fail as a production-quality detection if telemetry is incomplete, field normalization is inconsistent, risk/notable actions are misconfigured, or analysts lack useful investigation context. This lab was designed to exercise the whole pipeline rather than testing isolated searches.

ARCHITECTURE

Multi-tier lab design

  • Splunk Enterprise Security search head
  • Two-node indexer cluster
  • Cluster Manager / Deployment Server
  • Heavy Forwarder and Universal Forwarders
  • Linux and Windows telemetry
  • OpenLDAP identity/authentication source
  • AWS security telemetry including CloudTrail-oriented scenarios
  • Kubernetes/OpenShift-style monitoring scenarios

Portfolio rule: all screenshots, IP addresses, user identities, and configurations published here must come from the lab or be sanitized.

DETECTION LIFECYCLE

Telemetry → CIM → Detection → RBA → Investigation

  1. Generate / collect telemetry. Reproduce realistic authentication, cloud, endpoint, identity, and infrastructure events.
  2. Normalize data. Validate timestamps, sourcetypes, field extractions, calculated fields, aliases, and CIM alignment.
  3. Create detections. Build concise SPL or data-model-based logic tied to a defined threat behavior.
  4. Add context. Populate entities, threat objects, annotations, urgency, drilldowns, and investigation pivots.
  5. Apply RBA where appropriate. Assign meaningful risk objects, risk scores, and modifiers rather than generating excessive standalone alerts.
  6. Validate end to end. Confirm the search, ES finding/notable behavior, risk events, analyst visibility, and false-positive controls.
